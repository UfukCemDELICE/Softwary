# Changelog

All notable changes to softwary are listed here. The format follows
[Keep a Changelog](https://keepachangelog.com) and the project follows
[semantic versioning](https://semver.org). The date of a release is added when
it is tagged.

## 0.1.0

The first release.

### Checks and installation

- `./softwary verify` runs the project's checks from `commands.conf`, cheap to
  expensive, one line each, with exit codes 0, 1 and 2. An unconfigured check
  fails; a known debt is a waiver with a date and a scoped command.
- `./softwary doctor` reports installation and configuration problems.
- `install.sh` installs the package into a repository, listing every file first,
  and keeps the project's own files. `./softwary upgrade` replaces the managed
  files. Git hooks run the checks before commit and push.
- `./softwary sync` generates the skills, subagents and rules for Claude Code,
  Cursor and Codex from one source.

### Definition, blueprint and plan

- Skills `define`, `blueprint` and `plan`, and the checks behind them:
  `product check`, `blueprint check`, `plan check`, `trace`, `adr`, `changes`,
  `risk`. `approve` records your approval of the product definition and the
  blueprint as a digest of their files, so a later change is noticed.
- The architecture model (components), the data model, flows, state machines and
  architecture decisions, with Mermaid views generated by `views`.
- A critic subagent tries to break the blueprint before you approve it; a
  spec-analyst checks each spec before it is approved.
- TLA+ specifications with invariants written as plain sentences, checked by
  `formal check`, with a counter-example shown as steps for every invariant a
  deliberately broken variant violates. Specifications are kept in step with the
  code they cover (`formal verified`, `formal trace`, `states tests`); Lean
  proofs are optional for pure algorithmic cores.

### The loop

- `./softwary run`, `job`, `merge` and `queue`: jobs run in parallel (up to
  three) in their own git worktrees and branches, test first, through the gate,
  a pull request and CI, an independent reviewer and an approver. Merges are one
  at a time and are recomputed by a script that trusts no recorded result.
- Limits on rounds, minutes and tokens; state in files, so a dead session
  resumes; escalation with one concrete question.
- `guard` refuses protected paths, changes outside the slice's `touches` and
  loosened tests; R3 changes always come to a human.
- `eval` measures how many deliberately broken changes the reviewer catches; the
  loop merges by itself only above a threshold.
- Existing repositories: the `setup` skill asks for fix or waiver of every
  failing check; `define` and `blueprint` start from the code.

### Delivery and maintenance

- `ship`: a pull request from the integration branch to production with a
  release note; softwary never merges it and never deploys.
- `diagnose`: a bug is reproduced by a test first and fixed as a slice (`repro`).
- `drift`: where the code and the blueprint differ, with your decision for each.
- `status`, `next` and `handoff` for the state of the work and the next session.

### Cursor, Codex and release

- Models by tool: `models.conf` maps each model class to the model id of each
  tool (`cursor: opus = <id>`); `sync` writes it into the subagents of Cursor and
  Codex as well as Claude Code. `doctor` and `run start` fail when a tool that is
  on lacks an id and when the reviewer or the approver would use the
  implementer's model in any tool.
- The skills and subagents do not name a tool; tool notes are in
  `docs/guide/tools.md`.
- `install.sh --archive <tar.gz> --sha256 <digest>` and
  `./softwary upgrade <tar.gz> --sha256 <digest>` install from a release archive
  after checking its SHA-256. `tools/release.sh` builds the archive and
  `SHA256SUMS` deterministically.
- `./softwary uninstall [--yes]` removes the package and keeps your files;
  `./softwary version` prints the version.
- User documentation in English: `README.md` and `docs/guide/`. License: MIT.
  No telemetry.
